The four steps

One mode, four commands, and every other page in this repository is the detail behind one of them.

stepcommandwhat you have at the end
create uv run refactory ceo "<what it does>" --mode create --name my_pack a package on disk, registered, its mode smoke-scored
use it uv run refactory ceo my_pack/<mode> --intent "<what you want>" the mode ran on DSH, with its artifacts, and a person answered any gate
optimize it uv run refactory optimize my_pack/<mode> --epochs 4 --batch-size 6 --optimizer random --seed 5 a leaderboard, a report, and the edits that improved it
use it again uv run refactory adopt --run <run id> --as my_tuned the winner as a mode of its own, smoke-scored by the registry

interactive runs the mode on DSH under the CEO, with your terminal attached so a user gate reaches you; the run's directory holds facts.json, trace.json, state.json and the intent ledger. --workdir is optional and is resolved to an absolute path, because DSH takes it as the session's working directory.

The one thing that trips everybody up. Apart from create, edit and design, every mode in the box is deterministic op and gate nodes — they are offline fixtures, not examples of what a mode looks like. A mode calls a model when its graph has agent nodes, and only the brief decides that: ask for "an agent that drafts …" and the created mode makes that call. A mode with an agent node also needs a model at eval time, so registry smoke is not how you use it — it fails with agent node '…' needs a model client. Use interactive, the panel, or the CEO.

What a mode is

A Python class: a graph of nodes with typed knobs, and a score(). The graph is the architecture, the knobs are the parameters, and both are one serializable state dict — which is what lets an optimizer propose "set grid to 18" and "duplicate accept" as typed edits rather than as text.

The node kinds

  • op an operation: deterministic Python, no model
  • agent an agent task: may use tools and multiple model turns
  • gate a gate: routes on a verdict — `fn` computes it, `user` asks a person
  • fork a fork: the branches start together
  • join a join: the barrier every branch must reach
  • data a data node: the subgraph runs once per item

Only agent nodes call a model. Everything else is deterministic, which is why the fixtures are cheap to run and the loop can evaluate hundreds of candidates.

What it produces

A package directory in the workspace (.factory/packages/<name>) holding __init__.py, the mode module and its ops module; registered, validated, and smoke-scored. The intended structure of the mode is decided by the design node and checked by the validate gate before any review runs.

Its knobs

create knobwhat it does
attemptshow many times the emit step may be retried with the validator's reasons
review_attemptshow many times the review gates may reloop before stopping; defaults to the same as check_attempts
refusal_attemptsconsecutive refused emissions before the run stops
research_attemptshow many times the research step may be retried when its plan is not a plan or its findings were never written
design_attemptshow many times the strategy step may be retried when the intended graph does not hold together
task_refa Task class the produced mode must satisfy, as `module:Class` or a registered name (empty for none)
single_shotbuild the harness for one run of one thing, with no Task binding; the explicit alternative to naming a Task, and one of the two is required
smoke_timeout_swall-clock seconds allowed for each full mode validation pass, including its model calls; timeout fails creation
check_attempt_caphard cap on total check attempts including convergence grants; 0 or a value at or below the regular attempts disables the extension
sample_knobsknob values a validation run should use, as a JSON array of "NAME=VALUE" strings; without them the smoke runs the declared defaults, which for an input-taking mode is the built-in fixture
requires_inputthe inputs the produced mode must accept, comma-separated (e.g. `package` or `source_tree`); each must be received as a knob named after it or read from the run directory
data_nodebuild the package as a DataNode that runs its subgraph once per data item; naming a Task implies this, so the knob is only for a caller that wants to be explicit
namethe package to create (empty takes the name from the brief)
briefwhat the package should do, in the asker's words
revision_offor an edit: the <package>/<mode> being revised
allow_regressionfor an edit: skip original-mode execution and score comparison; still validate the revised mode (default false)

Running it

--verdict is the person's answer to gate_strategy, and dropping it is the one mistake worth naming: the run stops at that gate and tells you so, because a creation that approved its own plan is not a reviewed creation. On a paused run, console steer --verdict gate_strategy=proceed records the same answer and a resume replays it.

Ask for a model call in the brief. "Its graph must start with an agent node that drafts …" is the difference between a mode that calls a model and one that does not. Ask for a data node and a Task (--data-node --task my_pack.tasks:MyTask) and the validate gate checks you got one instead of taking your word for it.

Running it

The outer loop

A mode is one point in a space of modes: its knobs can be re-set and its graph can be re-wired. The outer loop searches that space. It proposes typed edits, refuses the ones that break the graph, evaluates what survives, and keeps what improves — and it reports what it refused, so a run that found nothing says why.

The eight steps

  1. init — read the mode's state, freeze what was frozen, write the run's first frame
  2. forward — evaluate the seed, so the search has a score to beat
  3. propose — the optimizer proposes a batch of edits — typed, never free text
  4. validate — every candidate is checked before it may cost a run (V2, V7, `E-shape`, …)
  5. backward — score the batch and turn it into a gradient over the knobs and nodes
  6. optimizer_step — the optimizer's own state advances (elites, population, archive)
  7. select_parents — pick what the next batch is proposed against
  8. report — the leaderboard, the rejections, and what the optimizer actually received

What it is not

It is not "ask a model to rewrite the mode". Every edit is from a closed catalogue of operations (set_knob, duplicate, insert_after, …), every candidate is validated before it may cost a run, and the score comes from running the candidate, not from an opinion about it. The one model-driven optimizer, autoresearch, is given the traces and proposes from the same catalogue as everyone else.

Optimizers — how the next candidates are proposed

An optimizer is the policy: which parent to breed from, how far to move, whether to keep a population. random samples the catalogue, hill_climb mutates the best so far, and autoresearch asks a model to read the traces.

optimizerhow it proposes
archiveSRF `scs`: breed from the best of everything seen, not just this epoch.
autoresearchAsk a model to read the traces and propose the next update.
evolutionarySRF `evox`: a tournament, so a weaker member can still breed.
hill_climbSRF `karpathy`: one candidate per round, from the best so far.
islandsSRF `openevolve`: sub-populations whose lineages never cross.
map_elitesSRF's own optimizer (`srf/lab/map_elites.py`): a champion per niche.
randomSample edits uniformly from the enabled catalogue.

How a mode becomes something that runs

One page of semantics, because everything else follows from it: a mode is data, the data is lowered to one IR, and two runtimes execute that IR.

  • The mode is data. Its architecture and its parameters are one serializable dict, so an optimizer can propose set_knob or duplicate as a typed edit, and a candidate is a value you can diff — not a code change somebody has to read.
  • The IR is the one interface. lowering.py turns the state into Workflow.to_dict(); the runtime knows nothing about Mode, Knob or score(). That is why the same graph runs on both runtimes and why "a mode means the same thing" is a testable claim rather than a hope.
  • Facts, then a number. A node declares what it reads, writes and produces; the executor enforces it, and score() reads the facts. A run that lied about its artifacts fails instead of scoring.

Datasets, Tasks and data nodes

A mode can walk a subgraph once per item — one benchmark instance, one row of a file, one directory — and a Task can supply those items and judge each pass.

  1. datadata — each item runs this
    • opworkrecord
      writes seen.json produces value
  2. opfinishdone
    writes done.json produces finished

Each pass writes the item to current_item.json in the run directory, so an op or an agent node reads the item it is working on rather than being told it in a prompt. Reusable harnesses take items from a source_path read as directory/jsonl/csv, or the bound Task's instances(); limit caps them; a named source that is missing is refused by name, because an empty selection and an unbound source must not look alike. The verdicts are recorded as item_scores, and score() reads what the Task decided instead of a number the graph guessed.

The Task protocol

hookwhat it is for

Both runtimes load items through one implementation (nn.executor.load_items), so the items a mode selects do not depend on which runtime is running it, and the equivalence test runs one data-driven mode on each and compares the facts. datasets.md is the long form.

Steering a run

A run is accountable to what it was asked for. The intent ledger is where that lives: it is seeded before the lowering, folded into every agent node's prompt, and read back when the run is judged.

entrywhat it carries
seedseed — what the run is for, in the asker's words; written once, before the lowering
noteinfo | correction | constraint — something said while it runs; a constraint must be respected, not merely known
verdictverdict — the answer a gate was routed on, so a resumed run replays it instead of asking again
  • The seed is written before the lowering, because the lowering is what carries it into the prompts; seeding afterwards would produce a run nobody steered.
  • A verdict is a decision the run routed on. Writing it down is what makes a resumed run the same run: re-asking would produce a second answer to a question already answered, and inventing one would produce a result nobody can account for.
  • Fidelity is checked, not assumed. A ledger that is missing, empty or holding the placeholder is reported, and given the run's agent outputs, a node that cited no entry — or a dangling one — is caught. Whether the work satisfies the intent still needs somebody to read it; that is what the gates are for.

Keeping it honest

Two runtimes, generated documents and a page of commands are three ways for a repository to start lying. Each one has a gate, and the gate is the answer to "is this tested?".

The equivalence test is the interesting one. It runs the same mode on the walker and on DSH and compares the facts, not the score: the two runtimes may differ in how they run a graph — one process against many, sequential branches against concurrent — and must not differ in what the run produced. Where they do differ, it is written down in the spine's README and the Agent Notes rather than discovered later.
